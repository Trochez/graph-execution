# Pax durable execution protocol — experimental
Use only when the current master exposes the project-owned in-process bridge tools. Do not shell-launch another agent CLI. Follow the original source plan, backlog, team and stage gates. This is a restricted candidate, not general native Pax agent-team support.

1. Load the four real skills via Harness Skills. For gexec, initialize the pipeline, read its exact plan, begin planner, write the legacy backlog and tasks artifacts, validate with the original DAG helper through the stage finish tool, inspect the analyzer output and verify source coverage. Only then begin team design, write the three team artifacts, run the existing graph helper and inspect the analysis. Never start execution before both verified stage receipts.
2. Pause if the local operator has not prepared the bundle with exact source hashes, task/owner mappings, relative file read/write paths, resource reservations, checked capability requirements, explicit verification argv and current approved model. The operator starts the dedicated worker in a separate terminal. The custom master may resume the same session and pipeline. For standalone native-plan-executor, the operator explicitly prepares an existing validated team and tasks without the wrapper.
3. Call gexec_runtime_info and gexec_start. Inspect gexec_status; Temporal releases verified prerequisites, enforces owner/paths/resources and caps active workers. The master owns approval and integration. Workers get bounded independent Pydantic Agent turns and explicit peer mailbox tools; they cannot shell, directly edit files or spawn. A peer question/answer needs a correlation ID. Use gexec_inbox, gexec_message and gexec_ack for master mailbox traffic.
4. For each verifying task inspect gexec_proposal and relevant read inputs. Review acceptance criteria and scope. Call gexec_review with apply, repair (one focused pre-effect repair within remaining model budget), or block. After apply, call gexec_verify to run actual operator-approved commands. An integrated check failure requires reconciliation, not an automatic rewrite. No downstream dependency is released until verified done.
5. Once all tasks are done, gexec_finalize runs final approved checks and writes records. If configured as gexec, it marks the legacy stage manifest complete only on successful final checks. Report actual task status, checked file hashes, verification evidence and limitations. If blocked, report concrete cause. Cancellation stops new work and drains bounded operations; it does not undo approved edits.
6. Resume by reopening the same local bundle, same Temporal server/data and worker queue, then query state. Do not start a duplicate workflow ID; inspect an existing journal intent without done receipt and reconcile uncertain effects manually. Preserve user changes. The local trusted namespace is not authenticated production infrastructure. Do not transmit secrets in plans, messages, code or outputs stored in workflow history.

Current restrictions: one approved OpenAI-compatible leaf route plus an explicitly selected master/lead route on the same endpoint, exact existing-parent UTF-8 files only (no deletes, rename or binary), bounded file and message sizes, no arbitrary shell tool or worker side effects, user-approved command execution by master, no mandatory unsupported human gate, and no automatic in-flight activity replay. No OS isolation against other local processes. These limits must be surfaced; do not claim production or other-host certification.

For lower master context overhead, use compact `gexec_status`/`gexec_wait`. After inspecting a specific proposal, `gexec_review_and_verify(task_id, attempt, evidence)` explicitly approves that exact attempt, waits for its existing integration and runs the approved checks. It does not approve an unseen proposal by itself. If integration remains in progress, wait; do not reapply. Full events remain in local execution records.
